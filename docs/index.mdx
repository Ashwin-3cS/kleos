**A memory harness that several AI agents share.**

Claude Code on your laptop, ChatGPT on your phone, whatever you add next — each
holds its own context window, makes its own decisions, and forgets them when the
session ends. Kleos is the layer underneath all of them: one record of what was
decided, **who decided it, and why**, that any of them can read before acting and
write to afterwards.

The problem it exists for is not storage. It is that the second agent does not
know there is a question to ask. So before acting, an agent states an intent and
is told:

```
device 3f9adead1c (labelled 'claude-code', device-authenticated) recorded
"project Lantern will use Neo4j." because "graph proximity is a hard
requirement and Postgres cannot do it" [rule: agent_delegate_supersedes].
Be aware of this before acting.
```

Three things in that line are the product. **Which device** — authenticated by an
Ed25519 key the owner registered, not by a name an agent chose for itself.
**Why** — the reason the deciding agent gave, stored with the decision. And **the
rule** — why the *record* moved, which is a different question from why the agent
decided.

Underneath: a **resolved record** rather than retrievable documents; memory as a
hierarchy of kinds; capabilities in a grant the owner's own device signs; and the
sensitive parts sealed inside a TEE (AWS Nitro Enclave, attested via NSM) so the
operator holds ciphertext. Identity comes from stacked OAuth signals verified
**inside the enclave**, not from a government ID.

## The bet, and the measurement

Everything here follows from one claim: that a resolved, timestamped record
beats a pile of retrievable documents. That claim is measured rather than
assumed.

<CardGroup cols={2}>
<Card title="Plain RAG answers with all three" icon="circle-question">
Ask "which database did we pick" and plain retrieval returns every past
decision with nothing to say which one holds. Nothing in the text of a
superseded decision says it was superseded.
</Card>
<Card title="Resolution answers with one, and its history" icon="circle-check">
The current claim, the chain that replaced the earlier ones, and the evidence
that moved each decision — with citations.
</Card>
</CardGroup>

| metric | resolved | resolved + history | plain RAG |
| --- | --- | --- | --- |
| recall | 87% | **100%** | 93% |
| cited | 100% | 100% | 0% |
| unmarked stale assertions | 0% | **0%** | 50% |
| forbidden records returned | 33% | 33% | 50% |

The useful part is where resolution *does not* help. The query graph alone
retrieves **less** than the baseline (87% vs 93%) — the gain comes from marking
superseded claims and from the supersession read, not from ranking. And graph
proximity costs precision across projects. See [Evaluation](/guides/evaluation)
for how to run it and why the absolute numbers are not quotable.

## What this is part of

The memory and permissions core of something larger: a voice-first personal
assistant, with Kleos as the layer that remembers and decides who may read what.
Privacy as a structural property rather than a promise — which means the
boundaries are where the design lives.

## What does not exist

No SDK, no smart contracts. Google and GitHub have consent and a sealed
refresh-token store but no `fetch` yet.

No **per-grant revocation**: revoking a device key invalidates every grant it
ever signed, which is the only lever there is. The dashboard works around it by
registering one key per agent, and that is a convention rather than an
enforcement. Nothing clamps a grant's TTL server-side either.

## Mocked

<AccordionGroup>
<Accordion title="Seal encryption is a reversible XOR in mock mode">
`enclave/src/services/seal.rs` has a deliberately fake implementation whose
output is prefixed `MOCK_SEAL_V1:` and whose scheme id says so. It is
obfuscation, not encryption, and it is labelled as such in the scheme id, the
blob prefix and every response field that carries it.

What is real today is the **custody path**: the plaintext exists only inside the
enclave, so when real Seal lands the invariant already holds and nothing outside
the TEE has to change.
</Accordion>
<Accordion title="Attestation documents are prefixed MOCK_ATTESTATION_">
So a mock document can never be mistaken for a real one — and since the
verifier landed, that prefix is a check rather than a convention: a mock is
refused unless `ATTESTATION_ALLOW_MOCK` is on, which `run_local.sh` sets and a
deployment does not.
</Accordion>
<Accordion title="OAuth providers short-circuit in mock mode">
Pass a token of the form `mock_google_<subject>` or `mock_github_<login>` and
the provider deterministically returns that identity, instead of dialing a
tunnel that does not exist locally.
</Accordion>
<Accordion title="Mock mode is per source, not global">
A connector gets fixture data only if its spec declares a `mock_factory`. The
Google and GitHub stubs raise in both modes. This replaced a short-circuit that
returned mock fixtures for *every* source, which made a half-built connector
look like it worked.
</Accordion>
</AccordionGroup>

## Stubs

These have real signatures and typed returns. They raise `NotImplementedError`
with the reason rather than failing silently.

| Stub | What is missing |
| --- | --- |
| **Walrus reads/writes** | `WalrusQuiltStore` has `LocalQuiltStore`'s interface and raises. It does **not** fall back to local disk: a deployment that believes it writes to Walrus and actually writes to the orchestrator's disk has a confidentiality bug, not a performance one. |
| **Walrus as a read path** | The blob read path is assembled and proven against `BLOB_STORE_DIR`. A Walrus-configured deployment has none, and reports `backend_not_wired` rather than "no body". |
| **Google and GitHub connectors** | Consent, code exchange and the sealed per-owner refresh-token store exist. Nothing yet *uses* a stored token to fetch. The missing half is a design question: how Python obtains usable credentials without the host ever holding the refresh token. |
| **Real Seal** | Needs a key-server committee and an on-chain owner policy object. |
| **`VoyageEmbedder`** | Needs an API key and an `EMBEDDING_DIM` matching that model, which must also match the Neo4j vector index. |
| **Credential-bearing actions** | The action broker is built and `attest.digest` works. `google.gmail.send` and `github.issue.comment` are declared and refuse: the enclave has no path from a sealed refresh token to a short-lived access token. |
| **Wallet and domain identity signals** | Reject explicitly rather than pretending to work. Trust tiers 3 and 4 are unreachable. |
| **Anything on-chain** | Grants are signed JWTs. `Scope` is shaped to become an on-chain grant object verbatim. |

`extraction/llm.py` is **not** a stub: it is wired and works the moment an API
key is set and `ORCHESTRATOR_MODE=live`. It has not been run against the live
API from this repository.

## Verified, but only as far as there is something to verify against

<Warning>
**`pinned` is unreachable today.** Verification establishes `signed_by_aws`
when a document chains to the AWS Nitro root. That excludes a plain HTTP
service pretending to be an enclave — today's actual exposure — and it does
**not** exclude a Nitro enclave running an image the operator built, because
only PCR0 distinguishes ours from any other. PCR0 comes from a release build on
real hardware, which has not happened (see below), so `ATTESTATION_EXPECTED_PCR0`
is unset and the strongest available outcome is the middle one.

The verifier reports which of the three it established rather than collapsing
them into a boolean, so a deployment can tell the difference. ADR 0026 has the
reasoning.
</Warning>

## Never run on real hardware

<Warning>
**`nitro` mode has never executed on a real Nitro Enclave.** This is the
load-bearing gap under every confidentiality claim in this documentation.

The `.eif` has not been built either: the Dockerfile needs the stagex image
cache, which is not present on the development machine. It is structurally
verified — `cargo build --release --no-default-features --features nitro -p enclave`
compiles cleanly, including the pinned `aws-nitro-enclaves-nsm-api` git
dependency — but compiling is not handshaking with Google.
</Warning>

A second bug found the same way, this time by building the verifier: the
`assemble` route committed the **whole base64 ciphertext** into the
attestation's `public_key` field, and NSM caps that field at 1024 bytes. A real
answer is several kilobytes, so that route would have been refused by the NSM
driver the first time it ran on hardware — and mock mode could never have shown
it, because the mock stub accepts any length. The commitment is now a SHA-384
digest over length-prefixed parts, which is 48 bytes whatever it covers.

A bug found while writing this down: until recently the enclave dialled
`http://127.0.0.1:<port>` — plaintext HTTP — into a tunnel that landed on port
443. A TLS listener cannot answer a plaintext request, so **no outbound enclave
call could ever have succeeded in `nitro` mode**. It went unnoticed because
`nitro` mode had never been run and `mock` mode short-circuits before the
network. Fixed and unit-tested; still unproven on hardware.

## Works, and not yet shippable

<Warning>
**Cross-session reasoning reads plaintext on the host.** `reason_across_sessions`
unseals every stored claim about a subject in an ordinary host process — the
same exposure as the resolver's, with a wider aperture. It is correct for
development and is not the end state: the model call belongs inside the enclave,
going out over the TLS tunnel the enclave already uses for OAuth.

It is also **unmeasured**, and it is the one thing here that writes claims
nobody asked for. There is no trigger threshold and no cost ceiling: only the
explicit call exists, and it is the single model call in the service not bounded
by top-k.
</Warning>

<Note>
**An enclave's outbound TLS hides the prompt from the operator and from nobody
else.** Whichever provider answers sees it. The confidentiality claim survives
because we are not that provider — and a reader will hear "nobody sees it", so
a self-hosted model is the only version where it survives being read plainly.
Extraction and consolidation have been run end to end against a local
llama.cpp, so that is a real option rather than a hypothetical one.
</Note>

## Known sharp edges

- **A grant cannot be revoked before it expires**, except per-object via
  `ObjectAcl.denied_agents` and wholesale by revoking the device key that signed
  it. There is no revocation list. Keep grant TTLs short.
- **Pending PKCE verifiers live in gateway process memory**, so a restart
  invalidates in-flight consents and a multi-instance gateway needs shared
  state.
- **`SEALED_TOKEN_STORE_URL` unset means an in-memory store.** Correct for mock
  mode; it silently forgets tokens on restart.
- **The orchestrator has no TLS of its own.** `POST /ingest` and `POST
  /remember` now require an owner session and derive the owner from it (ADR
  0027), and `/remember` is metered per owner — but a grant or a session still
  travels in a request body, so anything beyond localhost needs TLS in front.
- **A device must register both key halves at once.** Ed25519 signs and X25519
  receives, and the binding between them is the registration row — which is
  immutable, so a key registered with only a signing half can never gain the
  other. The failure arrives much later, as a 400 from `/memory/assemble` when
  an answer cannot be sealed to the device that asked.
- **A writing grant can cause stored content to be decrypted in a host
  process**, so that resolution can compare a new statement against existing
  ones. Nothing is disclosed to the agent, but it is the exposure that moving
  resolution into the enclave is meant to close.
- **A gateway error crossing MCP loses its reason.** It arrives at the agent as
  `Error executing tool <name>`; the explanation is in the orchestrator log
  only. Refusals were fixed by returning rather than raising; errors were not.
- **A retried write reports nothing written.** `record_decision` called twice
  with the same statement is correctly idempotent — the resolver recognises the
  content-addressed duplicate — but the second call comes back with no claim
  ids, so an idempotent write is indistinguishable from one that did nothing.
  Read it alongside what the call returned rather than on its own.

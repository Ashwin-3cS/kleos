title: "The confidentiality model"
description: "Three claims against three adversaries. They are not equally true, and this is the honest version."
---

"Encrypted, and the user owns it" is three different claims against three
different adversaries.

## 1. Confidential from the storage provider — delivered

Raw sensitive source content is sealed inside the enclave before it is written
anywhere, and OAuth refresh tokens are sealed inside the enclave before the
gateway persists them. Whoever runs the disk holds ciphertext.

<Warning>
In mock mode "sealed" means `MOCK_SEAL_V1:`, a reversible keystream XOR. It is
obfuscation, not encryption, and it is labelled as such in the scheme id, the
blob prefix, and every response field that carries it.

What is real today is the **custody path**: the plaintext exists only inside the
enclave, so when real Seal lands the invariant already holds and nothing outside
the TEE has to change.
</Warning>

A sealed body **can be read back**, and a read unseals under the agent's own
grant rather than an owner session it does not have — `POST /memory/seal/unseal`
verifies the grant, checks `scope.may_unseal`, and takes the owner from the
verified scope. That is a separate capability from reading, because seeing a
resolved claim and reading the raw transcript it came from are different
disclosures. See [Storage](/architecture/storage).

## 2. Confidential from other users and other agents — delivered

Via query-time permissions: every object carries an `ObjectAcl`, every query
carries a grant resolving to an authoritative `Scope`, and the check is pure,
total, deny-by-default, and runs between retrieval and assembly. Since there is
no revocation list, what backs this up is the read log.

## 3. Confidential from the operator — partly

<CardGroup cols={2}>
<Card title="Raw source content: yes" icon="circle-check">
The operator never holds a plaintext refresh token. The authorization code is
exchanged inside the enclave, the refresh token is sealed before the response
crosses back over VSOCK, and the gateway persists ciphertext it has no key for.
The access token is used inside the enclave to identify the account and then
dropped — never returned to the host at all. Only the enclave has the OAuth
client secret, so the host cannot repeat the exchange itself.
</Card>
<Card title="Derived memory, on a read: yes" icon="circle-check">
Closed by ADR 0024.
The host ranks on structure and embeddings, reads none of the candidates, and
hands them to the enclave still sealed; the enclave unseals, filters on real
content, assembles and **re-encrypts the answer to the device that asked**. The
host relays an opaque blob. Decrypting inside the TEE would have bought nothing
on its own — the re-encryption is the decision.
</Card>
<Card title="Derived memory, on a write: not yet" icon="circle-xmark">
Extraction and resolution still run in the Python orchestrator. The resolver is
the sharper of the two: it unseals *already-stored* claims on every ingestion to
compare against, so an operator watching one write sees far more than what was
written. Cross-session reasoning
(ADR 0025) is
the same exposure with a wider aperture — every claim about a subject at once.
</Card>
</CardGroup>

<Warning>
The write side is a **real gap, not a technicality**: for many purposes the
resolved record is the more sensitive artifact. Until it closes, **the product
should not claim the operator cannot read your memory. It can read what a write
touches. What it cannot read is your mailbox, or the answer to a read.**
</Warning>

<Note>
**The model does not have to move into the enclave, and an earlier version of
this page said it did.** The enclave already speaks TLS end to end for four
Google and GitHub upstreams: `/etc/hosts` maps the real hostname to a loopback
alias, socat forwards raw bytes over VSOCK, and the certificate is validated
inside the TEE, so the host moves a stream it cannot read. What enters the
measured image is an HTTP client, not an LLM — and `Upstream::host` is a
compile-time constant precisely so a host-supplied endpoint cannot redirect it.

What that does **not** buy is confidentiality from the provider that answers.
TLS from inside the enclave hides the prompt from the operator and from nobody
else. A self-hosted model is the only version where "we never see what it says"
survives a reader who hears it as "nobody does" — and extraction and
consolidation have both been run end to end against a local llama.cpp, so that
is a real option rather than a hypothetical one.
</Note>

`ENCRYPT_CONTENT_AT_REST` narrows this: an event's summary and body, a claim's
statement, an entity's name and aliases, and a citation's quote are sealed at
rest, while structure — ids, timestamps, edges, ACL fields, claim status — stays
in the clear so the structural reads keep working. Embeddings do too, until a
later stage. See ADR 0010.

## Where a plaintext refresh token exists

This is the invariant the connect flow is built around, and it is checkable.

| Step | Plaintext refresh token present? |
| --- | --- |
| `GET /auth/authorize` builds the consent URL | no token exists yet |
| Provider redirects to `/auth/callback?code=...` | no — a code is not a token |
| Gateway validates state, forwards the code to the enclave | no |
| **Enclave calls the provider's token endpoint** | **yes — inside the TEE, and only here** |
| Enclave verifies the account with the access token | yes (in-TEE) |
| Enclave seals the refresh token, drops the access token | leaves the TEE as ciphertext |
| Gateway decodes base64, writes bytes to Postgres | no |
| Orchestrator, Neo4j, logs, API responses | no — and no code path exposes it |

`gateway/tests/oauth_flow_tests.rs` runs a real enclave router in-process,
drives the real callback, and **searches the bytes that actually landed in the
store** for the mock plaintext. `gateway/tests/postgres_store_tests.rs` does the
same against real Postgres.

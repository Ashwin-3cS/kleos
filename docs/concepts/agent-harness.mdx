Kleos is built for more than one agent. Claude Code on one device and ChatGPT on
another each hold their own context window and make their own decisions, and the
record they share has to be able to say **which one decided what, and why**.

<Info>
This is the layer currently under construction. What is built is described
below; what is not yet built is marked, and the honest list is on
[Project status](/status).
</Info>

## Instance identity

A decision is attributed to a triple:

| Part | Where it comes from | Authenticated |
| --- | --- | --- |
| `agent_id` | the label the owner typed into the scope they signed | no |
| `device_id` | the registered device key whose signature the gateway verified | **yes** |
| `session_id` | minted by the orchestrator when a session opens | n/a — never supplied by the caller |

The session id is minted rather than accepted because an agent-chosen id is an
unauthenticated string two agents could collide on, by accident or on purpose,
and attribution is the entire point.

<Note>
"Device 1 decided this" is answerable with cryptographic force. "Claude Code
decided this" is answerable only as well as the owner labels their own devices —
so anything Kleos renders about an agent carries an `identity_basis` of
`device_key` or `label`.
</Note>

## Three states: stored, searchable, loaded

The distinction the whole design rests on. They are different states, and only
the first two are durable.

| State | What it means here | Enforced by |
| --- | --- | --- |
| **Stored** | A session block is sealed and written as a Quilt patch. No embedding is computed. | `blobs.put`, and the absence of an `upsert` |
| **Searchable** | In the vector index, reachable by retrieval and traversal. | the `:Memory` label plus an embedding — both only granted by `upsert` |
| **Loaded** | What one inference actually sees. Assembled per call, permission-checked per object, never stored as an object. | the read log is its only durable trace |

<Tip>
The loaded state having no persistent representation is deliberate. A stored
copy of every context window would be a second uncontrolled copy of the memory.
</Tip>

## Short-term memory: agent sessions

`:AgentSession` holds identity and bounds; the blocks themselves are sealed
blobs. A block is whatever the agent is working from — the turn it just took,
what a tool returned, a scratchpad, the contents of a file it opened.

<AccordionGroup>
<Accordion title="A session carries no `:Memory` label, and that is the mechanism">
The vector index and every traversal key on that label, so staying off it is
what makes "a scratchpad is stored and not retrievable" a property rather than a
convention. `:AgentRead` is off it for the same reason. One parametrised test
covers every harness label at once — it is what fails when someone adds a
convenient `SET n:Memory`.
</Accordion>
<Accordion title="A session cannot outlive the grant that opened it">
Clamped, not refused: a grant with ten minutes left should still be usable for
ten minutes. What it must not produce is a session surviving the capability that
authorised it.
</Accordion>
<Accordion title="Bounds are guards, not tuning">
400 blocks sits deliberately below `MAX_PATCHES_PER_QUILT` (660), so a session
never silently splits across two Quilts — correct for a backfill, wrong for a
thing that is supposed to be one coherent context.

A block over the byte cap is **refused, not truncated**. A truncated scratchpad
is one that silently lost the part the decision turned on, and the agent has no
way to tell.
</Accordion>
<Accordion title="Appending is not writing to memory">
`append_context` is deliberately **not** gated on a write-capable grant. It
produces nothing searchable, nothing carrying an ACL, and nothing the resolver
sees. The write gate is for the tool that mints a claim.
</Accordion>
</AccordionGroup>

## Memory kinds

Long-term memory is a hierarchy rather than a single pile:

<CardGroup cols={3}>
<Card title="Episodic" icon="clock-rotate-left">
Distilled decisions, facts and insights — preferences, codebase conventions.
</Card>
<Card title="Procedural" icon="list-check">
Reusable workflows: *how* a task is done.
</Card>
<Card title="Tacit" icon="lightbulb">
Consolidated heuristics the person never stated outright.
</Card>
</CardGroup>

Short-term is deliberately **not** a fourth kind. It is a different *state*, and
making it a kind would put session scratchpads in the same index as consolidated
facts — exactly the distinction the three states exist to draw.

<Info>
Memory kinds, write-capable grants, the mutation log, the briefing and
consolidation all exist. What is not built yet: the TEE action broker, where an
agent submits an intent and receives an acknowledgement rather than a credential.
</Info>

## Consolidation

The one thing that moves working context into long-term memory, and almost
nothing should move.

<AccordionGroup>
<Accordion title="A third prompt, not a third model">
Pointing the activity prompt at a scratchpad produces "the assistant decided
that the migration will use Postgres" — a claim attributed to nobody, about a
decision nobody made. So the consolidation prompt asks a different question:
what did this session *conclude* that outlives it, and of what kind. It says
outright that most sessions conclude nothing and that an empty list is the
common answer.
</Accordion>
<Accordion title="It may not summarise">
A consolidator emitting a paragraph per session would turn the memory back into
a pile of retrievable documents. The output is statements that can be
superseded, contradicted and reconciled by machinery that already exists.
</Accordion>
<Accordion title="The rule-based consolidator never invents a tacit claim">
In mock mode it recognises explicit cues — `Decision: ...`, `Procedure: ...` —
and nothing else. A regex cannot tell what a session concluded, and one that
guessed would write invented claims into a real person's memory under an
authenticated device id.

It emits **no tacit claims at all**. A tacit claim is an inference about how
somebody thinks, assembled from watching them; a fixture producing one would be
unfalsifiable, maximally sensitive, and attributed by a pattern match. A test
holds that.
</Accordion>
<Accordion title="Gated like a direct write, and idempotent">
Consolidating needs the same `may_write` a direct write does, because the
outcome is identical: a claim in the person's record. A session is not a licence
to write; the grant is.

A conclusion is dated to the **session**, not to when consolidation ran, so the
content-addressed record is the same on a retry — the resolver recognises the
duplicate and writes nothing. `claims` reports what that call wrote; the
session's `consolidated_into` is everything it ever produced.

One refused conclusion does not refuse the rest: a grant covering episodes and
not procedures keeps the episodes and reports what it would not keep.
</Accordion>
</AccordionGroup>

## Reasoning across sessions

Consolidation above asks what **one** session concluded, and it asks with no
stored memory and no other sessions in view. The resolver compares one new
statement against stored claims, pairwise and subject-scoped. Between them,
nothing had ever looked at a *subject* and asked what the sessions about it add
up to — so four sessions across two devices could all be about one project and
the harness would have formed a view of each separately and of none of them
together.

`reason_across_sessions` is the pass that does.
ADR 0025.

<AccordionGroup>
<Accordion title="Its output is a claim, not a stored block">
The decision, and it turns on one property: **a block cannot be superseded.**

Every correction mechanism in this service operates on claims. Store reasoned
prose instead and you have something that goes stale with an authenticated actor
attached, which none of the machinery built to fix exactly that can touch. The
Lantern decision reverses tomorrow; every claim updates, and the paragraph still
says what it said.

Note how directly this applies to what a pass concludes. "Decisions about this
subject have been reversed three times" is a statement with a shelf life — and
as a claim, a later pass's conclusion on the same topic supersedes it for free.

The rejected alternative was caching the briefing: safe, since every line traces
to a claim id, but it buys latency rather than capability, and a stale cached
block reads authoritative.
</Accordion>
<Accordion title="It may contradict a decision and may never replace one">
Authority is capped at `reference` **whatever the grant says** — even under
`may_supersede_owner`, which for an agent's own decision would make it a
`delegate` write.

This is the load-bearing constraint. A grant that says `may_supersede_owner` is
the owner delegating to *an agent they named*, not to a reasoning pass nobody
asked for, and a machine-derived inference quietly overwriting what somebody
decided is the inversion of what this service is for.
</Accordion>
<Accordion title="A third identity basis: derived">
`device_key` means the gateway verified a signature against a registered key.
`label` means all that is known is the `agent_id` the owner typed into a scope.
`derived` means **no identity was involved at all**.

The harness has no device, like the owner's own ingestion — but unlike the
owner's ingestion it is the *least* authoritative writer here rather than the
most, so the two cannot render the same way. A briefing says "the harness,
reasoning across sessions (derived, nobody asserted it)".

A caller cannot write *as* the harness: a grant carrying that `agent_id` is
refused by name rather than silently relabelled, because a relabel would hide
that somebody tried.
</Accordion>
<Accordion title="It reads claims, not scratchpads">
Consolidation already decided what of a session was worth keeping, and almost
nothing was. Re-reading the blocks in the one component with the widest view
would quietly reverse that — and claims carry what this needs anyway: the
statement, the status the resolver assigned, and the device and session behind
it.
</Accordion>
<Accordion title="Declining, concluding nothing, and concluding the same thing twice">
Three distinct non-failures. Below two sessions it **declines**, because one
session's claims were already reasoned over. It can run and conclude nothing,
which is the common case. And reaching conclusions a previous pass already
recorded writes none of them again: the record is dated to the newest claim it
was drawn from rather than to the clock, the same choice consolidation makes for
the same reason.
</Accordion>
</AccordionGroup>

## Why the record of reading is not memory

If a briefing were itself memory, then agent B reading about agent A's decision
would create a claim, which agent C's briefing would surface, which would create
another — a record whose growth is a function of **how often it is read** rather
than of what happened. Within a week the graph is mostly the system's commentary
on itself, and the resolver is comparing agent-about-agent material against the
person's actual decisions in the same subject neighbourhood.

What prevents it is one mechanism, used uniformly: every node that records the
harness's own activity stays off the `:Memory` label.
